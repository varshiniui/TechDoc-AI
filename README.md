# TechDoc-AI

A Retrieval-Augmented Generation (RAG) system that answers questions about your PDF documents - with real citations back to the source file and chunk.

**Live demo:** https://techdoc-ai-nuie.onrender.com/

> Hosted on Render's free tier — the first request after a period of inactivity may take 20–40 seconds to wake up.

---

## Overview

TechDoc-AI lets you drop technical PDFs into a `data/` folder, builds a searchable knowledge base out of them, and answers natural-language questions using only the content of those documents. Every answer cites the specific source chunk it came from, so responses are traceable rather than hallucinated.

It was built to explore a full RAG pipeline end-to-end: document ingestion, chunking, embedding, vector search, and grounded LLM generation — plus the practical constraints of deploying that pipeline on limited infrastructure.

## Features

- **PDF ingestion** — extracts text from any PDFs placed in `data/`
- **Smart chunking** — splits documents into overlapping, sentence-aware chunks rather than naive fixed-length cuts
- **Boilerplate removal** — automatically detects and strips repeated headers/footers/page numbers that would otherwise pollute every chunk
- **Deduplication** — drops near-duplicate chunks using word-overlap similarity, so repeated content doesn't crowd out the retrieval results
- **Semantic search** — FAISS vector index for fast similarity search over document embeddings
- **Grounded answers** — Groq-hosted LLM generates answers strictly from retrieved context, with inline citations like `[Source 3, 7]`
- **Source attribution** — every answer links back to the originating PDF and chunk

## How it works

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌──────────────┐
│  PDFs in    │ ──▶ │  Chunk +     │ ──▶ │  Embed +     │ ──▶ │  FAISS index │
│  data/      │     │  clean text  │     │  vectorize   │     │  (offline)   │
└─────────────┘     └──────────────┘     └─────────────┘     └──────────────┘
                                                                       │
                                                                       ▼
┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌──────────────┐
│  Answer +   │ ◀── │  Groq LLM    │ ◀── │  Retrieve    │ ◀── │  User asks   │
│  citations  │     │  generates   │     │  top chunks  │     │  a question  │
└─────────────┘     └──────────────┘     └─────────────┘     └──────────────┘
```

**Ingestion (offline, run once locally):** `ingest.py` reads every PDF in `data/`, strips repeated headers/footers, chunks the text, removes near-duplicate chunks, embeds each chunk with `sentence-transformers/all-MiniLM-L6-v2`, and writes the result to `vector.index` (FAISS) and `chunks.pkl`.

**Query time (deployed app):** when a question comes in, `rag.py` embeds it via Hugging Face's hosted Inference API (rather than loading the embedding model locally), searches `vector.index` for the closest chunks, and sends them to Groq's LLM to generate a grounded answer with source citations.

> **Why two different embedding paths?** Loading `sentence-transformers` at runtime pulls in PyTorch, which alone can use 400–600 MB of RAM — more than Render's free-tier 512 MB limit allows once the FAISS index and Flask process are also running. Ingestion only runs once, locally, so it can afford to load the model directly. The deployed app calls the same model remotely instead, keeping the live service lightweight.

## Tech stack

| Layer | Technology |
|---|---|
| Backend | Flask |
| Vector search | FAISS |
| Embeddings | Hugging Face Inference API (`all-MiniLM-L6-v2`) |
| LLM generation | Groq API |
| PDF parsing | PyMuPDF (fitz) |
| Deployment | Render |

## Project structure

```
TechDoc-AI/
├── app.py              # Flask routes (/ and /ask)
├── ingest.py           # One-time offline ingestion: PDF → chunks → embeddings → FAISS index
├── rag.py              # Query-time retrieval and answer generation
├── data/                # Source PDFs
├── static/              # CSS
├── templates/
│   └── index.html       # Chat UI
├── vector.index          # FAISS index (generated by ingest.py)
├── chunks.pkl            # Chunk text + source metadata (generated by ingest.py)
└── requirements.txt
```

## Setup

### 1. Clone and install

```bash
git clone https://github.com/varshiniui/TechDoc-AI.git
cd TechDoc-AI
pip install -r requirements.txt
```

### 2. Environment variables

Create a `.env` file in the project root:

```
GROQ_API_KEY=your_groq_api_key
HF_TOKEN=your_huggingface_token
```

- Get a Groq API key at [console.groq.com](https://console.groq.com)
- Get a Hugging Face token (Read access) at [huggingface.co/settings/tokens](https://huggingface.co/settings/tokens)

### 3. Add your documents and build the index

Place PDFs in the `data/` folder, then run:

```bash
python ingest.py
```

This generates `vector.index` and `chunks.pkl`, which the app reads at runtime. Re-run this any time you add or change documents.

### 4. Run locally

```bash
python app.py
```

Visit `http://localhost:5000`.

## Usage

Type a question about the ingested documents into the chat interface. TechDoc-AI retrieves the most relevant chunks and generates an answer citing exactly where it came from. If the answer isn't found in the documents, it says so rather than guessing.

## Deployment

Deployed on Render as a Flask web service via `gunicorn`. See [Setup](#setup) for the required environment variables — both `GROQ_API_KEY` and `HF_TOKEN` must be set in the hosting environment.
